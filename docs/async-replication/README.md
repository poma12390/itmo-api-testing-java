# ДЗ №5. Асинхронная работа с репликами

В проекте был одноузловой API задач. Для эксперимента добавил отдельный endpoint
`/v0/entity?id=<ключ>` с двумя профилями запуска. Координатор принимает PUT и GET,
реплики хранят массивы байтов в памяти.

## Как устроен кворум

Координатор отправляет запрос каждой реплике через `HttpClient.sendAsync`.
У клиента один пул из восьми потоков, размер задаётся `replication.http-threads`.
Контроллер возвращает `CompletableFuture`, поэтому поток Tomcat освобождается
на время ожидания сети.

`whenComplete` учитывает каждый ответ. Для трёх реплик достаточно двух
подтверждений `201` на PUT. На GET подходят `200` с версией и `404`. Из первых
двух таких ответов выбираю значение с наибольшей версией. Если оба ответа `404`,
координатор возвращает `404`. Общий дедлайн по умолчанию — 2 секунды. Ответ `503`
уходит раньше, если оставшихся реплик уже не хватит для кворума.

После решения вызываю `cancel(true)` у исходных HTTP-future. На репликах
включил HTTP/2, чтобы отменять поток внутри соединения. Координатор при старте
отправляет `HEAD` на каждую реплику и даёт соединениям перейти на HTTP/2,
даже если первый клиентский запрос сразу собрал кворум. Реплика сохраняет уже
принятую запись даже при отмене. [Javadoc HttpClient](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)

Координатор выдаёт возрастающие версии, а `ConcurrentHashMap.merge` атомарно
отбрасывает запоздавшие записи. Кворумы чтения и записи пересекаются. При чтении
после подтверждённого PUT хотя бы одна реплика вернёт эту или более новую версию.
Стенд рассчитан на одного координатора и фиксированный список реплик. Данные
хранятся до перезапуска реплик.

## Запуск

Собрать приложение на JDK 21 или 25. Для полного прогона с браузерными тестами
установить Chromium по инструкции в [README проекта](../../README.md#запуск).

```bash
./mvnw -Pui clean verify
```

Запустить три реплики и координатор в отдельных терминалах. Для реплик взять
порты 8081, 8082 и 8083.

```bash
java -jar target/api-testing-lab2-1.0.0.jar --spring.profiles.active=replica \
  --server.address=127.0.0.1 --server.port=8081

java -jar target/api-testing-lab2-1.0.0.jar --spring.profiles.active=coordinator \
  --replication.replicas=http://127.0.0.1:8081,http://127.0.0.1:8082,http://127.0.0.1:8083

curl -i -X PUT 'http://localhost:8080/v0/entity?id=demo' \
  -H 'Content-Type: application/octet-stream' --data-binary 'itmo'
curl -i 'http://localhost:8080/v0/entity?id=demo'
```

В `verify` прошли 101 API- и модульный тест, включая шесть новых, и 13
UI-тестов. Один UI-тест пропущен из-за [BUG-002](../web-testing/bugs/BUG-002.md).
Новые тесты проверяют HTTP/2, выбор версии, пересечение кворумов, отмену
HTTP-запроса, недостижимый кворум, дедлайн при неполном теле и запоздавшую
запись. Покрытие строк — 90,29%. [Журнал Maven](evidence/verify.txt)

## Стенд

Четыре JVM на одной машине, соединения по loopback. В последовательной сборке
координатор обходит реплики по порядку через `HttpClient.send` до того же
кворума. Хранилище, HTTP-клиент и правила выбора ответа общие для обеих сборок.
Патч применяется к отдельной копии исходников.

В каждом прогоне wrk2 — 4 потока, 64 соединения, 25 секунд и 128 заранее
заполненных ключей. Тело PUT и ответа GET — 256 байт. Сначала прогнал все
реплики без задержки. Во второй серии TCP-прокси добавлял 25 мс перед отправкой
данных к первой реплике из списка. PUT и GET измерял отдельно. Профили снимал
с JVM координатора при цели 1 200 запросов/с, чередуя блоки из 128 GET и 128 PUT.

При одинаковой цели без задержки обе сборки выдали примерно 1 200 req/s.
В этом прогоне p99 асинхронного GET уменьшился на 54%, PUT — на 66%.

С задержкой на первой реплике при 1 200 req/s p99 сократился в 8,0 раза для
GET и в 6,6 раза для PUT. Последовательный координатор ждёт первую реплику
в каждом запросе. Асинхронный обычно успевает собрать кворум на двух остальных.

При цели 3 500 req/s асинхронная версия обработала на 52% больше запросов.
Последовательная упёрлась примерно в 2 300 req/s. При 64 соединениях и времени
обработки около 27 мс верхняя оценка составляет около 2 370 req/s. Секунды
в p99 последовательной версии включают отставание от расписания отправки wrk2.
У асинхронного PUT p99 вырос до 26,70 мс при медиане 1,47 мс. Все основные
прогоны прошли без ошибок сокета и ответов вне 2xx/3xx.

Для каждой комбинации сделал один 25-секундный прогон. Цифры характеризуют
стенд на loopback и заданные скорости. [Настройки машины](evidence/environment.txt) · [Журналы wrk2](evidence/wrk2/)

В пробном PUT с HTTP/1.1 получил 164 req/s, 598 таймаутов и 91 ответ вне
диапазона 2xx/3xx. После перехода на HTTP/2 тот же прогон дал 1 188 req/s без
таких ошибок. Это сравнение двух прогонов с разным транспортом. Основная
таблица сравнивает обе сборки на HTTP/2. [Журнал прогона HTTP/1.1](evidence/wrk2/pilot-http1-put-1200.txt)

## Профилирование

async-profiler 4.6 записал CPU, alloc и lock в одну JFR на каждую сборку.
Интервал выборки alloc — 64 КиБ, порог lock — 1 мкс. Под профилировщиком обе
сборки держали около 1 200 req/s. p99 смешанного прогона составил 45,95 мс у
sync и 3,90 мс у async. [Прогон sync](evidence/wrk2/sync-profile.wrk.txt) · [Прогон async](evidence/wrk2/async-profile.wrk.txt)

| Событие | Sync | Async | FlameGraph |
| --- | ---: | ---: | --- |
| CPU, сэмплы | 2 199 | 3 772 | [sync](evidence/flamegraphs/sync-cpu.html) · [async](evidence/flamegraphs/async-cpu.html) |
| Alloc, оценка объёма за прогон | 2,56 ГиБ | 3,63 ГиБ | [sync](evidence/flamegraphs/sync-alloc.html) · [async](evidence/flamegraphs/async-alloc.html) |
| Lock, сумма времени ожидания | 0,72 с | 1,23 с | [sync](evidence/flamegraphs/sync-lock.html) · [async](evidence/flamegraphs/async-lock.html) |

- **CPU.** В sync 8,7% сэмплов проходят через `CompletableFuture.waitingGet` в
  блокирующем `HttpClient.send`. В async видна работа с HTTP/2 и отмена потоков.
  Через `Stream.cancel` проходит 4,6% сэмплов.
- **Alloc.** `byte[]` занимает около 40% в обеих сборках. В async суммарная
  оценка аллокаций выросла на 42%. На каждый входящий запрос создаются три
  HTTP-обмена, а в последовательном прогоне обычно достаточно двух.
- **Lock.** Основной вес у `HttpClientImpl` и `ReentrantLock`. Суммарное
  ожидание выросло с 0,72 до 1,23 с. Выигрыш в p99 получился за счёт сокращения
  ожидания реплик при большей работе HTTP-клиента.

FlameGraph можно открыть локально в браузере после скачивания HTML.

## Повторение замеров

Нужны Python 3.11+, wrk2 и async-profiler. Собрать обе версии из корня проекта.

```bash
./mvnw -DskipTests package
project="$PWD"
baseline="$project/.tools/replication-sequential"
mkdir -p "$baseline"
cp -R .mvn mvnw pom.xml src "$baseline/"
(
  cd "$baseline"
  patch -p1 < "$project/docs/async-replication/benchmark/sequential.patch"
  MAVEN_USER_HOME="$project/.m2" ./mvnw -DskipTests package \
    "-Dmaven.repo.local=$project/.m2/repository"
)

python3 docs/async-replication/benchmark/run.py \
  --wrk /path/to/wrk2 --asprof /path/to/async-profiler/bin/asprof \
  --async-jar target/api-testing-lab2-1.0.0.jar \
  --sync-jar "$baseline/target/api-testing-lab2-1.0.0.jar" \
  --output reports/async-replication
```

Скрипт использует порты 18080–18084, проверяет запись и чтение перед каждым
прогоном и сохраняет журналы, JFR и HTML FlameGraph. Для сборки wrk2 на Apple
Silicon использовал [ветку с LuaJIT 2.1](https://github.com/giltene/wrk2/pull/154)
на коммите `60a9a116103ffe999ea8d48421d024364b1ce3fb`. На macOS 26 генерировал
`obj/bytecode.c` через `luajit -b -t c` и компилировал в `obj/bytecode.o` через
`clang -c`, чтобы собрать Lua-модуль с системным линковщиком.
