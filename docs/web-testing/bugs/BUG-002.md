# BUG-002. Название только из Unicode-пробела сохраняется вопреки OpenAPI

| Поле | Значение |
| --- | --- |
| Статус | New |
| Тип | Функциональный дефект: валидация названия / расхождение с контрактом |
| Компонент | `TaskRequest.title`; POST `/tasks`, PUT `/tasks/{taskId}` |
| Версия | Tasks API 1.0.0, коммит `5c663ea7eadbbd830f438680f556f13639cfaecc` |
| Обнаружен | 17.10.2026 |
| Окружение | macOS 26.7.1, Java 25.0.2; встроенный браузер, 1280×720; `127.0.0.1:18080` |
| Severity | S3 Minor: сохраняется визуально пустое название; остальные операции доступны |
| Priority | P2: согласовать валидацию с опубликованной схемой |
| Повторяемость | U+00A0: POST 3/3 и PUT 3/3; дополнительно воспроизведён в Swagger UI |
| Связанные проверки | TITLE-18, TITLE-19; требование R-06 |

## Предусловия

Запущен отдельный экземпляр проверяемой версии по [инструкции](../README.md).
В TaskRequest контракта задано `title.pattern: "\\S"`.
Для PUT создана задача с непустым названием, её id получен из ответа.

## Шаги воспроизведения

1. В Swagger UI раскрыть POST `/tasks`, нажать **Try it out**.
2. Вставить тело именно с JSON-последовательностью `\u00a0`:

   ```json
   {"title":"\u00a0"}
   ```

3. Нажать **Execute**.
4. Прочитать созданную задачу по Location; убедиться, что title содержит
   один символ U+00A0, а не буквальный текст из шести символов `\u00a0`.
5. Повторить с тем же телом PUT для существующей задачи и прочитать её снова.

Эквивалентный запрос:

```bash
curl -i -X POST http://127.0.0.1:18080/tasks \
  -H 'Content-Type: application/json' \
  --data-binary @docs/web-testing/fixtures/bug-002-nbsp.json
```

## Ожидаемый результат

POST и PUT возвращают **422** с `field=title`; состояние хранилища не меняется.
Неразрывный пробел U+00A0 не удовлетворяет `\S` в семантике ECMA-262,
используемой JSON Schema. Таким образом, ожидание следует из опубликованного
контракта, а не из предположения о том, как должно выглядеть название.

Основание — `TaskRequest.title` в [проверенном контракте](../evidence/openapi-observed.json)
и [JSON Schema Validation, §6.3.3](https://json-schema.org/draft/2020-12/json-schema-validation#section-6.3.3).
U+00A0 включён в [определение пробельных символов ECMA-262](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-white-space).
В контрольной проверке выражение `/\S/.test("\u00a0")` возвращает false.

## Фактический результат

POST возвращает **201** и сохраняет название из одного U+00A0. PUT возвращает
**200** и заменяет прежнее название пробельным. GET подтверждает сохранение.

Ответ POST из веб-прогона, в котором невидимый символ показан JSON-экранированием:

```json
{"id":175,"title":"\u00a0","priority":3,"completed":false}
```

Такое же отклонение подтверждено в основном прогоне для U+2003 (EM SPACE).
ASCII-пробелы, табуляция и перевод строки отклоняются корректно — TITLE-08.
Название с пробелами вокруг непустого текста принимается — TITLE-20.

## Влияние и диагностика

В хранилище появляются задачи с визуально пустым названием, либо содержательное
название заменяется таким значением. Клиент, который применяет pattern из
OpenAPI, и сервер расходятся в решении о допустимости одного и того же тела.

Гипотеза причины: сервер использует `@NotBlank`, но не применяет правило
из `@Schema(pattern=...)` как серверный валидатор. Различается набор символов,
считаемых пробельными. Конкретную правку и её регрессию не выполнял.

на POST и PUT с 422 и без изменения данных. Обычный текст, текст с внешними
пробелами и короткое название с emoji остаются допустимыми.
