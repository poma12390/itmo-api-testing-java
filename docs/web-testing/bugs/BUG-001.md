# BUG-001. POST и PUT принимают данные после первого JSON-объекта

| Поле | Значение |
| --- | --- |
| Статус | New |
| Тип | Функциональный дефект: разбор тела запроса |
| Компонент | Создание и замена задачи; POST `/tasks`, PUT `/tasks/{taskId}` |
| Версия | Tasks API 1.0.0, коммит `5c663ea7eadbbd830f438680f556f13639cfaecc` |
| Обнаружен | 17.10.2026 |
| Окружение | macOS 26.7.1, Java 25.0.2; встроенный браузер, 1280×720; `127.0.0.1:18080` |
| Severity | S2 Major: некорректный запрос проходит проверку и изменяет данные |
| Priority | P1: сначала исключить запись по повреждённому телу |
| Повторяемость | POST 3/3 и PUT 3/3; дополнительно воспроизведён в Swagger UI |
| Связанные проверки | JSON-05, JSON-06; требование R-10 |

## Предусловия

Запущен отдельный экземпляр проверяемой версии по [инструкции](../README.md).
Параллельных запросов нет. В Swagger UI доступна операция POST `/tasks`.
Для PUT сначала создать задачу с названием `Исходная задача` и запомнить её id.
Перед запросом сохранить результат GET `/tasks?limit=100` для сравнения состояния.

## Шаги воспроизведения

1. Раскрыть POST `/tasks` в Swagger UI и нажать **Try it out**.
2. Заменить тело запроса на два последовательных объекта:

   ```text
   {"title":"Первый объект"}{"title":"Второй объект"}
   ```

3. Нажать **Execute** и посмотреть **Server response**.
4. Выполнить GET по Location из ответа и GET `/tasks?limit=100`.
5. Для проверки PUT отправить то же тело в PUT `/tasks/{id}` существующей задачи
   и повторно прочитать её по id.

Эквивалентный запрос из терминала:

```bash
curl -i -X POST http://127.0.0.1:18080/tasks \
  -H 'Content-Type: application/json' \
  --data-binary @docs/web-testing/fixtures/bug-001-trailing-object.txt
```

## Ожидаемый результат

POST и PUT возвращают **400**, `field=body`. Ни одна задача не создаётся
и не изменяется: JSON-текст должен содержать одно значение, а не два корневых
объекта. В OpenAPI для обоих методов предусмотрен 400 `Malformed JSON`.
Основание грамматики — [RFC 8259, §2](https://www.rfc-editor.org/rfc/rfc8259.html#section-2).

## Фактический результат

POST возвращает **201** и Location. Сохраняется задача из первого объекта,
второй объект игнорируется. PUT возвращает **200** и заменяет существующую
задачу данными первого объекта. Последующее чтение подтверждает изменение.

Сохранённый ответ POST из веб-прогона:

```json
{"id":174,"title":"Первый объект","priority":3,"completed":false}
```

Аналогичное отклонение обнаружено для `{"title":"До мусора"}oops`.
Обычные пробелы после объекта при этом допустимы и проходят JSON-07.
Это один дефект обработки данных после корневого значения, а не два независимых бага.

## Влияние и диагностика

Клиент получает успешный ответ на повреждённый запрос. Для PUT это означает
неожиданную замену уже сохранённых данных. Наличие эксплуатируемой уязвимости
по этому наблюдению не утверждаю.

Гипотеза причины: JSON-десериализатор читает первое корневое значение и не
проверяет остаток. В `JacksonConfig` нет включения `FAIL_ON_TRAILING_TOKENS`.
Исправление не выполнял и эту гипотезу изменением конфигурации не проверял.
