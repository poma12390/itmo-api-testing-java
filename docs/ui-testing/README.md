# Практическая работа. Автоматизация UI-тестирования

Продолжил работу с приложением задач из лабораторной №2. В предыдущей практике
проверял его через Swagger UI и составлял тестовую документацию. Теперь
автоматизировал пять сценариев этого же интерфейса с помощью Playwright for Java,
JUnit 5 и паттерна Page Object. Решение находится в ветке `codex/ui-testing`
того же репозитория.

Материалы курса отдельно не приложены. За основу взял задание, README,
OpenAPI и [предыдущий тест-дизайн](../web-testing/test-design.md).

## Цель и выбранные инструменты

Цель работы — сделать воспроизводимые UI-тесты основных операций с задачами,
отделить сценарии от устройства страницы и проверить результат действий
пользователя на работающем приложении.

| Инструмент | Для чего использовал |
| --- | --- |
| Java 21 | Язык и целевая версия проекта |
| Playwright for Java 1.63.0 | Запуск Chromium, поиск элементов, ввод и нажатия, ожидания |
| JUnit 5 | Жизненный цикл, тестовые методы и проверки результата |
| Spring Boot Test | Автоматический запуск приложения на свободном локальном порту |
| Maven Failsafe | Отдельный запуск UI-тестов через профиль `ui` |
| Jackson | Подготовка JSON и сравнение данных, прочитанных из интерфейса |

Выбрал Playwright, потому что он поддерживает автоматические ожидания готовности
элементов и отдельные контексты браузера. JUnit 5 уже используется в проекте,
поэтому второй тестовый фреймворк не потребовался.

## Объект тестирования

Объект — Tasks API 1.0.0 и его веб-интерфейс Swagger UI по адресу
`/swagger-ui/index.html`. Собственной HTML-формы задач в проекте нет:
пользователь раскрывает операцию, нажимает **Try it out**, заполняет параметры
или JSON, нажимает **Execute** и получает **Server response**.

Все создаваемые, изменяемые и удаляемые данные проходят через настоящий браузер
и интерфейс. Для подготовки и проверок тесты не отправляют прямые HTTP-запросы
и не подменяют ответы сервера. Единственное обращение к `TaskService` — очистка
локального хранилища между тестами. Код приложения и API-тесты прошлой работы
не менял.

Приложение запускается тестовой инфраструктурой на случайном порту. Данные
хранятся в памяти отдельного локального экземпляра; внешние сервисы не нужны.

## Пять автотестов

| ID | Метод JUnit | Данные и действия | Что проверяю |
| --- | --- | --- | --- |
| UI-01 | `createsAndReadsTaskAfterReload` | Создать задачу с кириллицей и кавычками, перезагрузить страницу, прочитать её и список | 201, положительный ID, точные поля, 200 при чтении, одна сохранённая задача |
| UI-02 | `appliesDefaultsToTaskWithMaximumTitleLength` | Передать только название из 100 символов | Верхняя граница длины принимается; `priority=3`, `completed=false`; результат сохраняется |
| UI-03 | `replacesTaskAndPersistsChanges` | Создать название из 1 символа с приоритетом 1, заменить все поля, указать приоритет 5 и `completed=true` | Граничные значения, ответ 200, прежний ID, новые поля после перезагрузки, отсутствие дубликата |
| UI-04 | `deletesTaskAndShowsNotFound` | Создать и прочитать задачу, удалить, повторить чтение и удаление | 204 без тела, смена предыдущего ответа GET с 200 на 404, сообщение `Task not found`, пустой список, повторное удаление 404 |
| UI-05 | `rejectsInvalidInputWithoutChangingStoredTask` | Создать контрольную задачу, выполнить POST с пробельным названием и PUT с приоритетом 6 | 422 и нужное поле ошибки; после отклонённых запросов список и исходная задача не изменились |

Применил классы эквивалентности для допустимых и недопустимых данных, границы
длины 1/100 и приоритетов 1/5/6, переходы состояний «создана → изменена → удалена».
Сценарии независимы: каждый сам создаёт нужные данные, получает ID из результата
и начинает с пустого хранилища. Порядок методов не задавал.

## Page Object и инкапсуляция

Структура тестового кода:

```text
src/test/java/ru/itmo/
├── api/
│   ├── TaskUiIT.java           — пять сценариев и JUnit-проверки
│   └── UiTestSupport.java      — сервер, браузер, изоляция и артефакты
└── ui/
    ├── UiResponse.java         — неизменяемый результат, прочитанный из UI
    └── pages/
        ├── SwaggerUiPage.java  — действия над задачами
        └── OperationPanel.java — общий компонент операции Swagger UI
```

`SwaggerUiPage` предоставляет методы `createTask`, `readTask`, `replaceTask`,
`deleteTask`, `listTasks` и `reload`. `Page`, локаторы и сериализация JSON скрыты
внутри Page Object. Тесты работают с пользовательскими действиями и данными;
ни одного CSS-селектора в `TaskUiIT` нет.

`OperationPanel` имеет пакетную видимость. Он раскрывает нужный блок, включает
редактирование, заполняет тело и ID, выполняет операцию и читает результат.
Компонент используется для всех пяти операций: при изменении разметки не нужно
исправлять каждый тест. Снаружи он не отдаёт `Page` или `Locator`.

Проверки предметного результата оставил в тестах. В Page Object находятся
только ожидания готовности интерфейса. `UiResponse` — record со статусом и
текстом тела ответа; метод `json()` позволяет сравнить структуру JSON целиком,
без зависимости от пробелов, подсветки синтаксиса и порядка полей.

Пример сценария на уровне Page Object:

```java
UiResponse created = ui.createTask("Сдать лабораторную", 2, false);
assertEquals(201, created.status());
long id = created.json().path("id").asLong();

ui.reload();
UiResponse fetched = ui.readTask(id);
assertEquals(200, fetched.status());
assertEquals(created.json(), fetched.json());
```

## Ожидания и устойчивость

Использовал `Locator.fill()`, `click()`, поиск кнопок по роли и точному имени,
а также повторяемые проверки Playwright `assertThat`. Локаторы ограничены
конкретной операцией; ID блоков берутся из `operationId` в контракте.

После **Execute** тест ждёт появления таблицы `.live-responses-table`, затем
читает статус и тело из её `tbody`. Справочные примеры в **Responses**
в результат не попадают. Перед повторным выполнением нажимается **Clear**
и проверяется исчезновение предыдущего ответа. Это важно, например, при
повторном GET после удаления: старый успешный ответ не должен дать ложный Pass.

Фиксированных задержек `Thread.sleep` нет. Тайм-аут действий — 10 секунд;
для повторяемых проверок используется стандартный тайм-аут Playwright.
Каждый тест получает новый `BrowserContext` с размером окна 1280×900 и локалью
`ru-RU`; cookies, cache и localStorage не переносятся. Chromium запускается один
раз на класс, а контекст закрывается после каждого теста. Запуск методов
последовательный, чтобы один экземпляр Playwright не использовался из разных
потоков.

## Запуск

Нужен JDK 21 или 25. Команды выполняются из корня репозитория.
При первом запуске скачать Chromium в локальную папку проекта:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.tools/ms-playwright" \
  ./mvnw exec:java -Dexec.args="install chromium"
```

Затем запустить API-тесты прошлой работы и пять UI-тестов:

```bash
./mvnw -Pui verify
```

Профиль сам задаёт путь к установленному Chromium и отключает автоматическую
загрузку других движков через `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`.
На первом запуске Maven
скачивает зависимости; при смене версии Playwright нужно повторить установку
браузера. Обычный `./mvnw verify` оставляет прежний набор API-тестов и не требует
установленного браузера. Команда `./mvnw -Pui test` выполняет только API-тесты:
UI-класс имеет суффикс `IT` и запускается Failsafe после этапа `test`.

Показать окно браузера:

```bash
./mvnw -Pui -Dui.headed=true verify
```

Выполнить один сценарий, например удаление:

```bash
./mvnw -Pui '-Dit.test=TaskUiIT#deletesTaskAndShowsNotFound' verify
```

На Linux при отсутствии системных библиотек установить браузер вместе с ними:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.tools/ms-playwright" \
  ./mvnw exec:java -Dexec.args="install --with-deps chromium"
```

На Windows установка из PowerShell:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = "$PWD/.tools/ms-playwright"
.\mvnw.cmd exec:java '-Dexec.args=install chromium'
.\mvnw.cmd -Pui verify
```

## Отчёты и дополнительные улучшения

После запуска появляются:

| Путь | Содержание |
| --- | --- |
| `target/failsafe-reports/` | Результаты пяти UI-тестов в XML и текстовом виде |
| `target/surefire-reports/` | Результаты прежних API-тестов |
| `target/ui-artifacts/environment.json` | Дата, Java, ОС, реальная версия Chromium и настройки запуска |
| `target/ui-artifacts/<имя метода>/page.png` | Финальное состояние страницы или состояние в момент ошибки |
| `target/ui-artifacts/<имя метода>/page.html` | HTML страницы для разбора проблемы |
| `target/ui-artifacts/<имя метода>/trace.zip` | Действия, DOM-снимки и сеть в трассировке Playwright |
| `target/site/jacoco/index.html` | Покрытие Java-кода приложения |

Артефакты сохраняются для каждого сценария, включая успешные. Контекст браузера
закрывается в `finally`. Для разбора сохранённой трассировки:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.tools/ms-playwright" \
  ./mvnw exec:java \
  -Dexec.args="show-trace target/ui-artifacts/deletesTaskAndShowsNotFound/trace.zip"
```

Обновил GitHub Actions: Chromium и системные библиотеки устанавливаются перед
прогоном, профиль `ui` запускается на JDK 21 и 25, отчёты и диагностические файлы
публикуются как артефакты даже при падении. Каталоги зависимостей и браузера
кешируются. Результат локальной проверки приведён в [доказательствах](evidence/README.md).

## Результат прогона

18.10.2026 выполнил чистую сборку на macOS 26.7.1 (aarch64), JDK 25.0.2 и
Chromium 153.0.8010.12 в headless-режиме. После установки зависимостей проверил
запуск без загрузок: Maven работал с флагом `-o`, в кеше браузеров остался
только Chromium и его служебные компоненты.

```bash
MAVEN_USER_HOME="$PWD/.m2" ./mvnw -o -B --no-transfer-progress -Pui clean verify
```

| Набор | Всего | Pass | Fail / Error | Skipped |
| --- | ---: | ---: | ---: | ---: |
| UI-тесты этой работы | 5 | 5 | 0 | 0 |
| API-тесты предыдущей работы | 95 | 95 | 0 | 0 |
| **Итого** | **100** | **100** | **0** | **0** |

Сборка завершилась с **BUILD SUCCESS** за 27,600 с. Покрытие строк Java-кода
приложения — **95,06%** (77 из 81), установленный порог 85% пройден.
Это покрытие кода приложения, а не процент покрытия пользовательских сценариев.

В [доказательствах](evidence/README.md) сохранил журнал сборки, результаты JUnit,
окружение, фактические ответы из финальных состояний страницы и пять скриншотов.
Локальный результат относится к JDK 25 и Chromium на macOS; запуск на JDK 21
и Linux предусмотрен конфигурацией CI.

Получился небольшой набор независимых UI-тестов, который можно запускать
повторно одной командой. Page Object скрывает разметку и повторяющиеся действия,
а сценарии проверяют создание, чтение, изменение, удаление и отклонение
некорректного ввода. Изоляция данных, ожидания и диагностические артефакты
помогают находить причину падения и поддерживать тесты при изменении интерфейса.

## Ограничения

Пять UI-тестов покрывают основные операции, границы и ошибки ввода, но не весь
чек-лист предыдущей практики. Известные [BUG-001–BUG-003](../web-testing/bugs/README.md)
в приложение не исправлял; пробельное название в UI-05 содержит обычные пробелы,
табуляцию и перевод строки, а не Unicode-пробелы из BUG-002.

Проверял Chromium на настольном размере окна. Firefox, WebKit, мобильная
компоновка, нагрузка и аудит доступности в этот набор не входят. Серверные
ответы проверяются через веб-интерфейс; самостоятельный интерфейс управления
задачами в проект не добавлял.
